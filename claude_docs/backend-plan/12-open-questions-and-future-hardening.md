## 3. Small API-surface gaps noticed while writing the endpoint plan

- ~~A dedicated `DELETE /me`...~~ **Closed.** `DELETE /v1/me` (full account deletion, `app/services/account_service.py`) now exists, distinct from `DELETE /me/data` (reset). Cascades via existing `ON DELETE CASCADE`; an already-issued access token stops working immediately since `get_current_user` re-looks-up the user on every request.
- ~~User-created category creation...~~ **Closed.** `POST /v1/categories` (`CategoryService.create`) lets a user add their own category (name + direction, no `key`).
- ~~User category edit/delete...~~ **Closed.** `PATCH /v1/categories/{id}` and `DELETE /v1/categories/{id}` now exist. Ownership follows the standing convention (09 §3): a system category (`user_id IS NULL`) or another user's is 404-equivalent, never a distinguishable "forbidden." Deleting a category still referenced by a transaction or an overlay's `ovr_category_id` is rejected with the new `category.in_use` (409) code rather than surfacing Postgres's FK error directly.

  Building this delete-guard surfaced a real, pre-existing bug: neither `transactions.category_id` nor `scenario_overlays.ovr_category_id` had an `ON DELETE` rule against `categories` (default RESTRICT). That's harmless for the single-category delete this guard covers, but it made full account deletion (`DELETE /v1/me`) intermittently fail — deleting a user cascades to *both* their categories (`categories.user_id ON DELETE CASCADE`) and their transactions/overlays (via `scenarios` cascading), and Postgres doesn't guarantee which of a table's several cascade paths fires first. Whenever a user had pointed a transaction or an overlay's override at one of their own custom categories, the category's cascade could fire before the transaction/overlay's, hitting the RESTRICT and failing the whole deletion with an unhandled `IntegrityError`. Fixed in migration `0011` by changing both FKs to `ON DELETE SET NULL` (not CASCADE — losing a category should orphan the reference, not delete the row; both columns are already nullable and the app already treats "no category" as normal). Found experimentally, not by inspection: it manifested as stale rows the test-cleanup fixture's `DELETE FROM users` couldn't clear.

## 7. Bilingual error/success messages (revises architecture §10)

Explicit user decision, made ahead of Flutter development starting: every error and every action-confirmation response now carries `message_en`/`message_ar` — ready-to-display bilingual text, generated server-side — alongside the existing machine `code`. The client picks by system language instead of maintaining its own translation table keyed off `code`. This is a genuine, deliberate revision of the architecture doc's original §10 rule ("the server never returns display text... the client owns all user-facing language"), not an oversight — recorded here the same way every other deviation in this doc is.

Three scoping decisions were made explicitly, not assumed:

1. **`code` stays.** The envelope is `{code, message_en, message_ar, params, request_id}`, not a replacement. The client still needs `code` to branch on behavior (e.g. `auth.token_expired` → refresh), independent of what's displayed.
2. **Success messages are scoped to action endpoints with no resource to return** — the ~9 that used to be a bare `204 No Content` (now `200 OK` with `{message_en, message_ar}`; a 204 can't carry a body at all). Endpoints that return the resource they just touched (`POST /scenarios`, `PATCH /transactions/{id}`, ...) are unchanged — the client already has what it needs to compose contextual copy from data it has, per screen-flow §10's "an action keeps its name through the whole flow" rule.
3. **Messages are generic per code, not interpolated with `params`** — a technical field name like `amount_minor` isn't natural-language material without its own translation, which would multiply scope considerably for limited benefit.

**The Arabic text is a first-pass machine draft, explicitly not reviewed copy** — architecture §10 (via screen-flow §6) already requires a native speaker's review before release for every user-facing string in the product, same as any Flutter-side ARB file would need. `app/core/errors.py`'s `ERROR_MESSAGES` and `app/core/messages.py`'s `SUCCESS_MESSAGES` are both flagged in their own docstrings as pending that review; swapping in reviewed text is a data change in those two files, not a redesign.

Built: `ERROR_MESSAGES` (27 codes) in `app/core/errors.py`, with an import-time check that it never drifts out of sync with `ERROR_STATUS`; `SUCCESS_MESSAGES` (9 keys) in the new `app/core/messages.py`; the shared `ActionResult` schema (`app/api/schemas/common.py`); all 9 action routes changed from 204→200; pure-unit tests for both registries (`tests/core/test_bilingual_messages.py`) plus real-HTTP envelope tests (`tests/api/test_error_envelope.py`).

## 9. Gaps found during Flutter screen-by-screen verification (`API-ENDPOINTS.md`)

Distinct from §8 above: these aren't M1 §11 items, they're small contract gaps surfaced by actually walking each Figma screen against its endpoint (the process behind `API-ENDPOINTS.md`) — real HTTP request against the running backend, not inspection. Recorded here the same way as every other deviation in this doc.

1. **Sign Up / Register had no `name` field at all.** `POST /auth/register` only ever took `email` + `password`; `display_name` was left `null` until a separate `PATCH /me/settings` call. **Decided: `name` is now required on register**, stored as `user_settings.display_name` at account-creation time (`UserSettingsRepository.create_default`'s new `display_name` param) — never null for a new user.
2. **Initial balance entry had no floor on the amount.** `PUT /me/balance`'s `current_balance_minor` accepted any integer, including negative — no locked doc says whether a negative Current Cash Balance (overdraft/debt) should be allowed. **Decided: rejected.** New error code `balance.negative_not_allowed` (422); `SettingsService.update_balance` now checks `current_balance_minor >= 0` before the existing date checks. Zero is still allowed.
   - **Still not addressed:** `scenarios.current_balance_override_minor` (the per-plan override of the same Current Cash Balance concept, set via `POST /scenarios` / `PATCH /scenarios/{id}`) has the identical gap — no non-negative check. The Plans screen verified in item 3 below turned out to be plan-name-only (no override field exposed there), so this is still open — worth applying the same rule once a screen that actually sets the override comes up (e.g. an "advanced" create option, or the plan-detail edit screen described in `08-api-endpoints-plan.md`'s `PATCH /scenarios/{id}` row).
3. **Plan creation's name field had no non-blank check.** `POST /scenarios` (and, sharing the same validation path, `PATCH /scenarios/{id}` rename and `POST /scenarios/{id}/duplicate`'s explicit `name`) accepted a blank (`""`) or whitespace-only (`"   "`) name, which would show up empty in the plan switcher and compare picker. **Decided: rejected**, using the existing generic `validation.invalid` (422) code rather than a new one — `ScenarioService._validate_name()` checks `name.strip()` is non-empty before the existing name-uniqueness check, applied at all three call sites. Duplicate's "omit `name` to get `<source> (copy)`" default behavior is unchanged — only an explicitly-passed blank/whitespace name is now rejected instead of silently falling back to that default.
4. **The transactions list had no way to show removed rows, and no way to re-discover an overlay's id after the fact.** Two related gaps surfaced together by the Transactions screen's "All / Active only / Removed only" filter (§5.1/§4.4 of the screen-flow spec's badge system): `GET /scenarios/{id}/transactions` only ever returned rows currently in effect (own/inherited/overridden/added) — an excluded overlay was silently dropped by `ScenarioResolver` (a bare `continue`), so there was **no endpoint at all** that could return a "removed" row. Separately, an overridden row's response never carried the *overlay's own* id (only the underlying Base transaction's id) — but editing or reverting that overlay requires `PATCH`/`DELETE /scenarios/{id}/overlays/{overlay_id}`, and the client only ever learned that id once, at the moment it created the overlay; there was no way to recover it on a later app open. **Decided: build both.**
   - New domain-only `Origin.EXCLUDED` value (`app/domain/enums.py`) — deliberately **not** added to the engine's own `Origin` (`app.engine.types`): an excluded row is never fed to the engine, so `ScenarioResolver._resolve_rows()` (the single most sensitive function in the backend, per its own module docstring) is completely untouched. A new, separate method, `resolve_excluded_for_api()`, computes excluded rows independently, returning a new `ExcludedRow` dataclass (Base's field values verbatim — an exclude overlay has no `ovr_*` fields to apply).
   - `GET /scenarios/{id}/transactions` gained a `?filter=active|removed|all` query param (default `active`, byte-identical to the endpoint's prior-only behavior, so every existing test kept passing unchanged). `removed` is always empty on the Base Plan (exclusion is a derived-scenario-only concept).
   - `TransactionOut` gained `overlay_id: uuid | None` — populated for `overridden` and `excluded` rows (the two kinds of row an overlay backs), `null` for `own`/`inherited`/`added`. Fetching the list is now sufficient on its own to get the id needed for every subsequent overlay `PATCH`/`DELETE` call — no separate lookup endpoint was added or needed.
   - Verified end-to-end against a real running server: override + exclude a Base row from a derived plan, confirm `filter=active`/`removed`/`all` each return exactly the expected set with the right `overlay_id`, then restore the removed row via `DELETE /scenarios/{id}/overlays/{overlay_id}` using only the id from the `removed` response (never one remembered from creation) and confirm it's back to `inherited`.
5. **The seeded system category set didn't match the Figma category-picker mockup at all.** Migration `0004` originally seeded 20 keys (`salary, bonus, rental_income, business_income, investment_income, other_income` / `rent, utilities, groceries, transportation, dining, subscriptions, insurance, loan_payment, savings_transfer, entertainment, healthcare, education, childcare, other_expense`) with no relationship to the design's 12 (`salary, freelance, business` / `housing, loans, bills, subscriptions, everyday, transport, fuel, health, other`) — different keys, different counts, no overlap beyond `salary`/`subscriptions`. **Decided: replace the seed wholesale to match the design exactly**, rather than trying to map one set onto the other. Migration `0015` deletes the old 20 and inserts the new 12 (forward-only, per this project's migration discipline — `0004` is left untouched, `0015` is what actually runs); `downgrade()` restores the original 20 precisely, for reversibility. Safe with zero real user data at stake: `transactions.category_id` and `scenario_overlays.ovr_category_id` are `ON DELETE SET NULL` (migration `0011`), so any reference to a removed key just becomes uncategorized rather than failing. Confirmed both directions (`alembic upgrade head` / `downgrade -1`) actually produce the right 12/20 rows. Also confirmed while checking this: the category picker doesn't filter by the transaction's own direction (income categories and expense categories sit in one ungrouped grid in the mockup) — nothing server-side enforces `category.direction == transaction.direction` either, so this is already consistent, not a gap.
6. **The Plans list's per-card summary line ("X modified · Y removed · Z added") has two possible data sources that silently disagree.** Verifying the Plans screen (create/edit/delete/duplicate/archive/unarchive all already worked, confirmed live) surfaced that the natural-looking shortcut — `GET /forecast/compare`'s own `drivers` list, already tagged `added`/`removed`/`modified` — is the *wrong* source for this count: a driver is dropped whenever a change doesn't move the total (`app/engine/compare.py`'s `_drivers()`, `if contribution == 0: continue`). Verified live: overriding a transaction's name only (same amount) produced zero drivers, while `GET .../transactions?filter=all` correctly still reported it as `origin: "overridden"` — the same row that shows a `Modified` badge on the Transactions screen (§9 item 4 above). **Decided: the structural count from `transactions?filter=all` backs this line, not `compare`'s drivers** — so it agrees with the badges shown everywhere else in the app, at the cost of one extra API call per plan on this screen (Base's card: 1 call, its own forecast; every other plan's card: 2 calls, compare + transactions list — no dedicated list-summary endpoint exists or was added, consistent with the "no dashboard/charts endpoint" rule). `compare`'s `drivers` list keeps its existing, correct purpose: ranking *financially meaningful* differences for wherever the actual Compare screen shows "what's driving this," not for counting structural edits.
7. **A compare driver's "$X/mo" figure had no way to avoid being diluted.** Verifying the Compare screens ("Compare plans" picker, "Compare results" with its "What's driving this" list) confirmed almost everything is already fully buildable with zero new backend work — the header balances, the delta and its percentage, the chart lines, and the drivers list itself (already ranked by impact, already tagged exactly `modified`/`added`/`removed`) were all already there. One real gap: a driver's `total_contribution_minor` is a total over the *whole* comparison horizon, and the only divisor available to turn it into a monthly figure was `horizon_months` — which dilutes anything that doesn't span the full window. Verified live: a mortgage added 2 months into a 120-month horizon has a real, steady cost of SAR 9,000/mo, but `total_contribution_minor / horizon_months` reported SAR 8,850/mo instead. **Decided: add `active_months`** (the count of distinct months the driver actually occurs in — computed in the engine's `_drivers()`, alongside `total_contribution_minor`, using the same B-preferred-over-A convention already used for the driver's `name`/`direction`) to `Driver` (`app/engine/models.py`) and `DriverOut` (`app/api/schemas/forecast.py`). A client now computes the undiluted rate as `total_contribution_minor / active_months`. Verified live: the same mortgage now reports exactly SAR 9,000/mo. Two new tests (engine-level and API-level) pin the mid-horizon-start case specifically, since a driver that spans the whole horizon can't distinguish the two divisors at all.
8. **Profile photo (screen-flow F2) — not in any locked doc at all, a genuinely new feature, not a gap in something already specced.** Zero backend infrastructure existed for this beforehand: no field, no upload endpoint, no file storage. Three decisions were made explicitly before building:
   - **Storage: local disk**, not cloud object storage — matches this build's standing no-Docker/no-cloud-infra-yet posture (same reasoning as the in-memory rate limiter, §1). **Explicitly acknowledged as throwaway infrastructure**, not a permanent architecture: this will not survive most real hosting (an ephemeral or non-shared filesystem) and is expected to move to real object storage before or during deployment. See `02-configuration-and-environment.md` §5.
   - **No separate upload endpoint** — folded into the existing `PATCH /me/settings` as one more optional field (`avatar_base64`, raw base64, a `data:` URI prefix tolerated and stripped; `remove_avatar: true` to clear it), by explicit product decision, rather than a dedicated multipart route. Kept the endpoint's existing JSON contract completely intact — every already-shipped currency/locale/display_name test kept passing unchanged.
   - **Email stays permanently unchangeable after account creation** — the Profile screen's Email field is display-only, never submitted. Considered and explicitly rejected building a real change-email flow (would have needed a uniqueness check plus a decision on re-verification, which isn't possible without an email provider — the identical constraint that already ruled out forgot-password-via-email, §8 item 8).

   Built: `user_settings.avatar_filename` (migration `0016`, folded back into `phase1-system-architecture.md` §5.3 same as the refresh-tokens addendum), a computed `avatar_url` property (never a second stored column) building a relative `/static/avatars/<uuid>.<ext>` path, `app/core/avatar_storage.py` (magic-byte format sniffing — never trusts a claimed extension/MIME type; new-file-written-before-old-file-deleted ordering, so a rejected upload never destroys a working photo), two new error codes (`avatar.invalid_image`, `avatar.too_large`), a static mount in `app/main.py`, and explicit cleanup of the stored file in `DELETE /me` (full account deletion) — deliberately **not** in `DELETE /me/data` (reset), matching how `display_name`/`currency_code`/`locale` are already treated as account preferences, not "data" in the RFP §4.8 sense.

   Verified: 269 tests passing (9 new), lint/mypy/import-linter clean, real HTTP smoke test uploading a real PNG alongside a name change in one call, downloading it back from the static route byte-for-byte, then confirming account deletion actually removes the file from disk (not just the DB row) with a follow-up 404.
