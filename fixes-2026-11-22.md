## UAT-002: Duplicate / Clone Scenario

**Client ask:** Duplicate in each scenario's action menu. Copy transactions, overrides, assumptions and forecast config into a new independent scenario. Prompt for a new name, open the copy for editing. Editing or deleting either copy must not change the other.

**Decision (2026-11-22):** keep live Base inheritance (D-13). A duplicate of Base copies nothing; Base edits flow into every plan that inherits. "Independent" means the source and the copy do not affect each other, which already holds.

**Current state:** `POST /scenarios/{id}/duplicate` exists (`app/api/v1/scenarios.py`, `ScenarioService.duplicate`). Body `{ "name": optional }`, default name `"<source> (copy)"`.
- Derived source: overlays and own transactions are copied with new ids. Tested in `tests/api/test_scenarios.py` (independence, overlays, own transactions, live Base inheritance).
- Base source: nothing copied, by design.
- Archived source rejected (`scenario.archived`). Blank or taken name rejected (`validation.invalid`, `scenario.name_taken`).

**Gaps and work:**
1. **Balance override not copied (bug).** `ScenarioService.duplicate` creates the copy with only a name, so `current_balance_override_minor` is lost. Copy it from the source (derived sources only; Base has none).
   - Test: duplicate a plan with an override and assert the copy has the same value; changing one afterwards leaves the other unchanged.
2. **"Assumptions and forecast configuration": nothing to do in Phase 1.** There are no stored assumptions (the engine `assume` step is a no-op) and the horizon is a request parameter, not stored on the plan. Document this in the reply to the client.
3. **Optional, for the "open the copy for editing" flow:** none required. The response already returns the new `ScenarioOut` (id, name), which is all the client needs to select it.
4. **Docs:** update the `POST /scenarios/{id}/duplicate` section in `claude_docs/API-ENDPOINTS.md` to say the balance override is copied. Sync the Flutter copy of the doc.

**Acceptance:** all existing duplicate tests still pass, plus the new override test. Full suite (281+) green, ruff and import-linter clean.

**Effort:** small (under half a day). No schema change, no migration, no engine change.

## UAT-003: Create Scenario from Existing

**Client ask:** New Scenario offers Start from Scratch / Start from Base Plan / Start from Existing Scenario. Starting from an existing scenario creates an independent copy, not a permanently linked one unless explicitly chosen. Example: Buy Property + Car from Buy Property, then add the car payment and compare. No double-counting of inherited or overridden transactions.

**Current state (no new endpoint needed):**
- Start from Existing = `POST /scenarios/{id}/duplicate` with a `name` (see UAT-002). It never creates a parent link (architecture §5.1), so the copy is independent of its source.
- Start from Scratch / Start from Base Plan = `POST /scenarios` with a list of names. Because every plan inherits Base live (D-01, D-13), both produce the same result: a plan with Base's items and no changes of its own. The backend has no "empty plan with no Base items" and should not gain one.
- Double-counting is already guarded and tested: `tests/api/test_scenarios.py::test_duplicate_of_base_with_transactions_yields_each_item_once`, `test_duplicate_of_derived_scenario_copies_its_overlays`, `test_duplicate_keeps_live_base_inheritance`, and `tests/api/test_m1_plan_cases.py` case 25.15. Compare (`GET /forecast/compare`) works on any two plans.

**Gaps and work:**
1. **Depends on UAT-002 backend fix** (copy `current_balance_override_minor`). Nothing else to change.
2. **"Unless explicitly chosen" linked scenario: not built (decided).** A permanent parent link between derived plans would reopen D-01 and architecture §5.1 (overlay-on-Base only, no parent chain). Copy only.
3. **Add tests that pin the client's example** (Buy Property, then Buy Property + Car as a copy):
   - Duplicate a derived plan that has an override and an own transaction, then add a car payment to the copy only. Assert the source's forecast is unchanged and the copy's differs by exactly the car payment, each item counted once.
   - Run `GET /forecast/compare?a=<source>&b=<copy>` and assert the difference equals the added item.
4. **Docs:** state in `claude_docs/API-ENDPOINTS.md` that "create from existing" is the duplicate endpoint, and "start from Base" is plain create.

**Acceptance:** the two new tests pass, the full suite stays green, no schema or engine change.

**Effort:** very small (tests and docs only, plus the UAT-002 fix).

## UAT-004: Custom Recurrence within Transactions

**Client ask:** Recurrence > Custom, shown as "Every [4] [Months]" with units Days, Weeks, Months, Years. Positive whole-number interval, start date, optional end date, preview of the next occurrence dates. Consistent handling of 29/30/31, leap years, forecast expansion and scenario copying.

**Change-control note:** this amends **D-08** (frozen set of 7 recurrences, "no custom cron"). **Approved 2026-11-22.** The request is not cron; it is a bounded "every N unit" rule that fits the existing clamp-never-drift engine. Update architecture §4 and the build spec when the work starts.

**Current state:**
- `Recurrence` (`app/domain/enums.py`, `app/engine/types.py`) = one_time, weekly, biweekly, monthly, quarterly, semiannual, annual. It is a Postgres enum (`recurrence`) used by `transactions.recurrence` and `scenario_overlays.ovr_recurrence`.
- `app/engine/expand.py` already has two generic mechanisms: day-based (fixed step, `DAY_INTERVALS`) and month-based (anchor day from `start_date`, clamped by `calendar.clamped_date`, step from `MONTH_INTERVALS`). Custom fits both with a variable step.
- No endpoint returns "next dates" for a rule that has not been saved yet.

**Design (recommended):** keep the 7 values and add `custom`, plus two fields that are only set when `recurrence = custom`:
- `recurrence_interval` (integer, 1 to 999)
- `recurrence_unit` (`day` | `week` | `month` | `year`)

Years are 12-month steps, weeks are 7-day steps, so the engine needs no new algorithm. The existing seven stay as they are (no data migration, no change to current behaviour).

**Work:**
1. **Migration `0018`.**
   - Add enum value `custom` to `recurrence` (needs an autocommit block in Alembic).
   - New enum `recurrence_unit`.
   - Add `recurrence_interval` and `recurrence_unit` to `transactions`, and `ovr_recurrence_interval` / `ovr_recurrence_unit` to `scenario_overlays`.
   - CHECK constraints: for custom both fields are present and the interval is greater than 0; for every other value both are null. Same rule on the overlay columns. Keep `one_time_has_no_end` and `valid_range` as they are.
2. **Engine (`app/engine`).** Add `CUSTOM` to `Recurrence`; add `interval` and `unit` to `ResolvedTransaction`. In `expand`, resolve any recurrence to (kind, step): day or week units go through `_expand_day_based` with `step = n` or `7n`; month or year units go through `_expand_month_based` with `step = n` or `12n`. Anchor day always comes from `start_date` (clamp-never-drift). Refactor the two dictionaries into one lookup so the seven existing values behave exactly as before.
3. **Schemas and validation (`app/api/schemas/transactions.py`, `overlays.py`).** Accept and return `recurrence_interval` and `recurrence_unit`. 422 `validation.invalid` (with `params.field`) when custom is missing either field, when the interval is not a whole number from 1 to 999, or when the two fields are sent with a non-custom recurrence. Overlay PATCH that changes the recurrence away from custom must clear the override fields.
4. **Services.** `transaction_service`, `overlay_service` (`_merge`, `_validate_merged`) and `scenario_resolver` must carry the new fields through resolve, merge and validate. `ScenarioService.duplicate` and `overlays.copy_all` must copy them (scenario copying consistency).
5. **Preview endpoint (new).** `POST /transactions/preview-occurrences` (authenticated, stateless, nothing saved). Body: `recurrence`, optional interval and unit, `start_date`, optional `end_date`, `count` (default 6, max 24). Response: `{ "dates": ["YYYY-MM-DD", ...] }`. It calls the same engine `expand`, so the preview can never disagree with the forecast. The Flutter app must not compute dates itself (zero calculation on the client).
6. **Export (`app/api/schemas/export.py` and the CSV export).** Include the two new fields.
7. **Tests.**
   - Engine fixtures: every 10 days; every 4 months; every 6 months; every 2 years; every 3 weeks; anchor day 29, 30 and 31 with monthly and 4-monthly steps (clamp, then back to the anchor day, never drift); Feb 29 every year and every 2 years across leap and non-leap years (2028-02-29, 2029-02-28, 2030-02-28, 2032-02-29); window boundaries; end date inclusive; start after window.
   - Hypothesis property tests: custom 1 month equals `monthly`, 3 months equals `quarterly`, 6 months equals `semiannual`, 12 months equals `annual`, 7 days equals `weekly`, 14 days equals `biweekly`, for random start dates and windows. Determinism and reconciliation properties must still hold.
   - API: validation matrix; create, patch and read back; overlay override to custom and back; duplicate copies the fields; export includes them; forecast and compare with a custom transaction; preview endpoint (auth required, count cap, invalid input).
   - Migration: upgrade and downgrade on `pfmf_test`.
8. **Docs.** `claude_docs/API-ENDPOINTS.md` (schemas and the new preview endpoint), the architecture and build-spec recurrence sections (D-08 amended), and `engine/README.md`.

**Rollout risk:** the Flutter client parses recurrence strictly (since the 2026-10-17 audit fixes), so an older APK that receives a `custom` transaction will fail to parse it. Release the backend and the new Flutter build together, or accept that only users on the new build create custom rules.

**Acceptance:** "every 10 days", "every 4 months", "every 6 months" and "every 2 years" produce the right dates in the forecast; Feb 29 and day 31 behave per the clamp rule; the preview endpoint matches the forecast's dates exactly; the seven existing recurrences are unchanged (all current tests and golden fixtures pass); full suite, ruff and import-linter green.

**Effort:** medium (about 3 to 4 days including migration, engine tests and docs).

**Status:** TODO (D-08 approved).

## UAT-005: Custom Forecast Duration and Calendar End Date

**Client ask:** Keep quick filters (6 months, 1 year, 3 years, 5 years). Add Custom Duration (X months / X years) and "Forecast Until" with a date picker (for example 30 November 2027). The same interval applies to the chart, monthly table, final projected balance and scenario comparison. The end date must follow the forecast start and respect documented engine limits.

**Current state:**
- `GET /scenarios/{id}/forecast` and `GET /forecast/compare` take `horizon` (whole months, 1 to `max_horizon_months` = 120). The window starts on the first day of the anchor month (`balance_as_of`'s month by default) and ends on the last day of month `anchor + horizon - 1` (`app/engine/forecast.py`). Output is one row per month.
- Quick filters and "X months / X years" need no backend change: the client converts them to months (up to 120).
- There is no way to end the forecast on a specific day.

**Work (only for "Forecast Until"):**
1. **New optional query parameter `until=YYYY-MM-DD`** on both the forecast and compare endpoints. `horizon` becomes optional; exactly one of `horizon` or `until` is required (422 `validation.invalid` otherwise).
2. **Semantics.** The forecast covers the anchor month through the month containing `until`. In that last month, only occurrences on or before `until` count, and its closing balance is the balance on `until`. Every earlier month is unchanged.
3. **Engine.** Add an optional `until` argument to `engine.forecast()`: `window_end = min(end of the horizon, until)`. The engine stays a pure function (no clock, no I/O); the service converts `until` to a month count. The existing horizon path must produce byte-identical output (golden fixtures).
4. **Validation.** `until` must be on or after the first day of the anchor month and no later than the last day of month `anchor + max_horizon_months - 1`. New error key `forecast.invalid_until` (422), with English and Arabic messages and an entry in the bilingual-messages test.
5. **Response.** Add `until` (the date used, or the last day of the final month when `horizon` was used) so the client can label the result. Compare returns the same `until` for both plans, and both sides always use the same window.
6. **Tests.** Mid-month and month-end `until`; `until` equal to the anchor month's first day; before the anchor (422); beyond 120 months (422); both or neither of `horizon` and `until` (422); an occurrence exactly on `until` is included, the next day is excluded; a recurring item clamped near `until` (31st, Feb 28/29); `horizon` output unchanged; compare with `until` and with a Base-versus-derived pair; reconciliation property (closing balance equals opening plus the sum of the included occurrences).
7. **Docs.** `claude_docs/API-ENDPOINTS.md` forecast and compare sections.

**Decision (2026-11-22):** mid-month cut-off, as specified above. Month-granularity-only was considered and rejected.

**Acceptance:** `until=2027-11-30` returns months from the anchor through November 2027, the chart, table, final balance and compare all use that window, and every existing `horizon` test and golden fixture is unchanged.

**Effort:** small to medium (about 1.5 days).

**Status:** TODO.

## UAT-007: Monthly Transaction View

**Client ask:** Transactions screen with Previous/Next month arrows and direct month/year selection. For the selected month show each occurrence (including those generated by recurring rules) with name, signed amount, effective date, recurrence type and optional start/end period; monthly Total Income, Total Expenses and Net Cash Flow; a Monthly Summary/Reports view; empty states; browse past and future months; future occurrences clearly distinguished; a recurring item shows its own due date in the month, not the series start date.

**Current state:**
- `GET /scenarios/{id}/transactions` returns rules (one row per transaction with `start_date`, recurrence), not dated occurrences.
- `GET /scenarios/{id}/forecast?include_occurrences=true` returns occurrences, but only from the anchor month forward, for the whole horizon, and with no recurrence or start/end details. It cannot show months before the anchor and is heavy for a single month.
- Phase 1 is plan-only (D-02): there are no posted or actual transactions. Every occurrence is a planned entry; "past" and "future" can only mean the date compared with today.

**Work:**
1. **New endpoint `GET /scenarios/{id}/occurrences?month=YYYY-MM`.**
   - Resolves the plan (Base, inherited, overridden and added items; excluded rows omitted) and expands every transaction over that one calendar month with the same engine `expand` used by the forecast.
   - Response: `month`, `currency_code`, `items[]`, and `totals { income_minor, expense_minor, net_minor }`.
   - Each item: `transaction_id` (the source rule, for navigating to edit), `name`, `direction`, `amount_minor` (positive, direction separate per D-10), `on` (the occurrence date), `origin` (own / inherited / overridden / added), `recurrence`, the custom interval and unit when present (UAT-004), `start_date`, `end_date`, `category` fields as in `TransactionOut`.
   - Sorted by date, then name.
2. **Range.** `month` may be any month from 120 months before to 120 months after the anchor month; otherwise 422 `validation.invalid` (`params.field = month`). Past months before the anchor are allowed because expansion is pure and needs no balance.
3. **Reconciliation guarantee.** For any month inside a forecast, the endpoint's totals equal that month's `income_minor`, `expense_minor` and net in `GET /forecast`. Add a property test for it, plus a test over a Base plan, a derived plan with overrides and exclusions, and a custom recurrence.
4. **Past and future.** No server field is needed: the client compares `on` with the device date. Do not add "posted" or "actual" wording anywhere (there are no actuals).
5. **Reports view (decided):** totals only (income, expenses, net) as already in the response. No `by_category` breakdown in this round.
6. **Tests.** Month with a monthly, a weekly and a one-time item; January shows the January due date for a series that started in November; month before the series start is empty; end-date boundaries; clamped day 31 in February; excluded rows absent; plan isolation (user A cannot read user B's plan, 404); invalid and out-of-range month.
7. **Docs.** `claude_docs/API-ENDPOINTS.md` (new endpoint) and the architecture note that Transactions renders from this endpoint (§9.1 currently says everything renders from `/forecast`; amend it).

## UAT-008: Editable Transaction Date

**Client ask:** A Transaction Date with a calendar in Add and Edit. Past and future dates allowed within documented business rules. One-time items appear only in their month; recurring items use a start date and schedule. Editing should clarify whether the user changes a single occurrence, future occurrences or the whole series.

**Current state:**
- The API already accepts and stores `start_date` on create and PATCH, and for plan overrides (`ovr_start_date`). `end_date` must not be before `start_date`, and one-time items cannot have an end date (DB constraints).
- Nothing else limits the date (no lower or upper bound), so year 0001 or 9999 would be accepted.
- Editing always changes the whole series (PATCH the transaction) or, for an inherited item in a derived plan, the plan's overlay. There is no "single occurrence" or "this and following" edit.

**Work, in three parts:**

**Part A: the date itself (no model change).**
1. Add sanity bounds on `start_date` and `end_date` for create, PATCH and overlays (for example 2000-01-01 to 2100-12-31), with `validation.invalid` and `params.field`. This also covers the unbounded-input note from the 2026-10-17 audit.
2. Document the rule that a transaction dated before the forecast anchor month has no effect on the forecast (the window starts on the first day of the anchor month), and that it still appears in the monthly view (UAT-007).
3. Tests for the bounds, one-time items appearing only in their own month, and a recurring item's due dates for each month.

**Part B: "this and following occurrences" (new, needs a decision).**
- Split a series at a chosen occurrence date: end the original the day before and create a new series from that date with the edits. It must be one atomic call, for example `POST /scenarios/{id}/transactions/{tid}/split` with `{ "from": "YYYY-MM-DD", "changes": {...} }`.
- Inherited items in a derived plan cannot change Base (architecture §9.2): the plan's overlay ends the Base item with `ovr_end_date = from - 1` and the plan gets a new added transaction starting at `from`. Both writes in one transaction.
- Editing Base itself from the Base plan splits the Base series (this affects every plan that inherits it, as editing Base does today).
- Needs tests for Base, derived, overridden and added items, plus duplicate and export behaviour.
- Effort: medium (about 2 to 3 days).

**Part C: "single occurrence only" (new capability, quote separately).**
- Needs a new table of per-date exceptions (skip, or override the amount for one date) tied to a transaction or overlay, engine `expand` support for exceptions, resolver, duplicate, export, forecast, month view and compare changes, plus new property tests. It touches the overlay model (D-01) and is the largest piece of the UAT list.
- Effort: large (about 5 to 7 days). Deferred; not in this round.

**Decision (2026-11-22):** Part A only. Parts B and C are deferred and out of scope for this round; they stay documented above in case the client asks again. The Flutter app shows "Changes apply to every occurrence" instead of an occurrence-scope choice.

**Acceptance (Part A):** a transaction can be created and edited with any date within the bounds; a date outside them returns 422; one-time items show only in their month; the full suite stays green.

**Effort:** Part A small (about 0.5 day).

**Status:** Part A DONE (2026-11-22; bounds on `start_date`/`end_date`/overlay dates, 7 new tests, API doc updated). Parts B and C deferred.

## UAT-011: Show full exact amounts
